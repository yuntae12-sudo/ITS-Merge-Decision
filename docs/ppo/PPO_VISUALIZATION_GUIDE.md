# PPO Rollout Visualization Pipeline

VISUALIZATION / DIAGNOSTIC TOOLING ONLY. This pipeline never trains,
tunes, or modifies PPO, the Frozen 14D observation, KEEP/FOLLOW/MERGE/
STOP action semantics, Reward V0, the Frenet planner, LTV-MPC, or the
canonical TRAIN/VALIDATION split. It only loads an already-trained PPO
checkpoint, runs it through the real, frozen
`MergeEnvironment(downstream_mode="frenet_mpc")`, and renders what
actually happened.

## 1. Purpose

Given any trained PPO checkpoint, answer three questions with real
data:

- What does a **Success** episode actually look like, frame by frame?
- What does a **Collision** episode look like, and where did it go
  wrong?
- What does a **Timeout** episode look like -- did the policy never
  decide to MERGE, or did the downstream controller stall it?

The pipeline is checkpoint-agnostic: any future PPO run (Reward V1,
hyperparameter tuning, multi-seed training) can be visualized with the
exact same command, no code changes.

## 2. How this differs from Phase 0 log playback

`scripts/run_scene.py` / `scripts/run_rollout.py` (Phase 0) replay a
**raw WOMD log** -- no simulated control, no `MergeEnvironment`, no
policy of any kind. They predate the Merge environment and PPO
entirely.

This pipeline runs a **real closed-loop simulation**: the restored PPO
policy makes KEEP/FOLLOW/MERGE/STOP decisions, the frozen
`BehaviorExecutor` + Frenet planner + LTV-MPC (`CommonDownstream`)
convert each decision into a physical command, and Waymax's bicycle
model integrates the ego vehicle's real state one physical step at a
time. Every plotted position, TTC, and reward is a real value read out
of that closed loop -- never replayed from a log, never hand-drawn, and
never interpolated.

## 3. What "post-training checkpoint evaluation" means

Every episode this pipeline renders is generated by **replaying a
trained checkpoint's frozen weights** against `MergeEnvironment`,
*after* training has finished. It is **not** the same episode the
policy experienced *during* training (rollout collection during
training uses a different, evolving set of weights at every update,
and this pipeline can be pointed at maneuvers the checkpoint never even
saw). Every manifest/summary this pipeline writes is stamped:

```
POST-TRAINING FINAL-CHECKPOINT EVALUATION
```

so a reader can never confuse it with a training-time rollout replay.

## 4. Basic usage

```bash
PYTHONPATH=. python scripts/visualization/visualize_ppo_run.py \
  --checkpoint outputs/ppo_checkpoints/p6_baseline_50m_50u_100s_seed0.pkl
```

Default behavior:

- **Policy mode**: `deterministic` (argmax via `PPOPolicy.act_deterministic`)
  -- reproducible by construction, no seed needed.
- **Scope**: `checkpoint` -- evaluates exactly the maneuver set the
  checkpoint's own `config_snapshot["maneuver_ids"]` recorded (i.e. the
  maneuvers it was actually trained on). Never the canonical VALIDATION
  split unless you ask for it explicitly.
- **Downstream mode**: `frenet_mpc` (the only mode Phase 4/5 research
  evaluators may use).
- **Max episode steps**: 100 (matches `MAX_EPISODE_HORIZON_FRAMES`).
- **Render count**: **up to 5 episodes per outcome category**
  (success/collision/timeout/offroad) get a full render (`rollout.gif`,
  `trace.csv`, `trace.png`, `rollout_4panel.png`, `summary.json`). If an
  outcome category has fewer than 5 episodes in the evaluated scope,
  all of them are rendered (never padded, never crashes).
  `outcome_index.csv` always contains **every** evaluated episode,
  regardless of how many get rendered -- see Section 5.

Rendering more, or none at all:

```bash
# Render EVERY evaluated episode per outcome (not just the first 5)
PYTHONPATH=. python scripts/visualization/visualize_ppo_run.py \
  --checkpoint outputs/ppo_checkpoints/p6_baseline_50m_50u_100s_seed0.pkl \
  --render-all

# Outcome scan only -- outcome_index.csv + selected_episodes.json, no
# GIF/figure rendering at all (fast iteration)
PYTHONPATH=. python scripts/visualization/visualize_ppo_run.py \
  --checkpoint outputs/ppo_checkpoints/p6_baseline_50m_50u_100s_seed0.pkl \
  --scan-only

# Raise/lower the default per-outcome cap (ignored with --render-all/--scan-only)
PYTHONPATH=. python scripts/visualization/visualize_ppo_run.py \
  --checkpoint outputs/ppo_checkpoints/p6_baseline_50m_50u_100s_seed0.pkl \
  --max-per-outcome 10
```

`--scan-only` and `--render-all` are mutually exclusive -- passing both
is a CLI error.

Other useful invocations:

```bash
# Specific maneuvers only -- an explicit --maneuver-ids scope always
# renders EVERY one of the maneuvers you named (never truncated by the
# default per-outcome cap, even if several of them share an outcome)
PYTHONPATH=. python scripts/visualization/visualize_ppo_run.py \
  --checkpoint outputs/ppo_checkpoints/p6_baseline_50m_50u_100s_seed0.pkl \
  --scope explicit --maneuver-ids MAN_0001,MAN_0002

# Stochastic policy (categorical sampling), fixed seed for reproducibility
PYTHONPATH=. python scripts/visualization/visualize_ppo_run.py \
  --checkpoint outputs/ppo_checkpoints/p6_baseline_50m_50u_100s_seed0.pkl \
  --policy-mode stochastic --policy-seed 0

# Explicit VALIDATION evaluation (never automatic -- see Section 5 of
# docs/ppo/P6_EXPERIMENT_GUIDE.md: canonical VAL is reserved for a
# final, already-decided model, never for picking between experiments)
PYTHONPATH=. python scripts/visualization/visualize_ppo_run.py \
  --checkpoint outputs/ppo_checkpoints/p6_baseline_50m_50u_100s_seed0.pkl \
  --scope split --split validation

# Force additional specific maneuver(s) into the collision selection
# (added to, never replacing, the default/--render-all picks)
PYTHONPATH=. python scripts/visualization/visualize_ppo_run.py \
  --checkpoint outputs/ppo_checkpoints/p6_baseline_50m_50u_100s_seed0.pkl \
  --select-collision MAN_0071
```

## 5. Output structure

```
outputs/ppo_visualizations/<RUN_ID>/
├── manifest.json
├── outcome_index.csv          # ALWAYS one row per evaluated maneuver
├── selected_episodes.json     # which maneuver_ids got rendered, per outcome
│
├── success/<MANEUVER_ID>/     # up to 5 by default, or --render-all's full set
│   ├── rollout.gif
│   ├── trace.csv
│   ├── trace.png
│   ├── rollout_4panel.png
│   └── summary.json
├── success/<MANEUVER_ID_2>/...
├── collision/<MANEUVER_ID>/...
├── timeout/<MANEUVER_ID>/...
└── offroad/<MANEUVER_ID>/...   # only if an offroad episode exists
```

`RUN_ID` defaults to the checkpoint filename stem (override with
`--run-id`).

- **`outcome_index.csv`** is the full quantitative record: one row per
  **evaluated** maneuver, ALWAYS -- if the evaluation scope has 50
  maneuvers, this file has exactly 50 rows, regardless of the render
  policy in effect. It is never truncated to match how many episodes
  got rendered. Columns: `maneuver_id, outcome, termination_reason,
  steps, merge_commit_step, policy_decision_count,
  intervention_rate`. Outcome is read directly from
  `MergeEnvironment`'s own `terminated`/`truncated`/`termination_reason`
  -- never re-judged by a separate rule.
- **`selected_episodes.json`** is the **qualitative rendering
  subset**: which maneuver_ids actually got a full render, per outcome
  category, as a **list** (not a single id):
  ```json
  {
    "success": ["MAN_0001", "MAN_0002", "MAN_0004", "MAN_0006", "MAN_0007"],
    "collision": ["MAN_0005", "MAN_0012"],
    "timeout": ["MAN_0003"],
    "offroad": []
  }
  ```
  How many ids land in each list depends on the active render policy
  (Section 4): up to `--max-per-outcome` (default 5) per category by
  default, every matching episode with `--render-all`, or an empty
  render set entirely with `--scan-only` (the file itself is still
  written, just with a resolved-but-unrendered selection). An empty
  list means that outcome had zero episodes in the evaluated scope
  (never a crash) -- `manifest.json`'s per-run notes explain why.
  Selection order within a category is always a fixed, deterministic
  rule: stable sorted `maneuver_id` order, first N.
- **`manifest.json`**: checkpoint path/git_sha, current repo git_sha,
  reward_version, seed, `ppo_update_step`/`global_env_step`, network
  config, the full evaluated maneuver list, policy mode, downstream
  mode, max episode steps, the selected episodes, and a `render_policy`
  block recording exactly which rendering mode produced this run --
  `{"mode": "representative_per_outcome", "max_per_outcome": 5}` (default),
  `{"mode": "all"}` (`--render-all`, or an explicit `--maneuver-ids`
  scope), or `{"mode": "scan_only"}`. This is what lets you look back
  at an old run and know *why* only 5 GIFs exist instead of 33.
- Per-episode **`trace.csv`**: one row per physical step -- decision
  metadata, PPO action probabilities (NaN on post-commitment
  auto-executed frames -- see Section 9), reward components, the full
  14D observation, downstream/intervention diagnostics, and ego pose.
- Per-episode **`trace.png`**: a stacked diagnostic time-series (see
  Section 7).
- Per-episode **`rollout_4panel.png`**: a paper/PPT-style 4-moment
  figure (Decision Start / Pre-Merge-or-Last-Decision / Merge Commit /
  Terminal Outcome), reusing `scripts/figures/fig2_rollout_sequence.py`'s
  rendering conventions but driven by this episode's real PPO-selected
  actions.
- Per-episode **`summary.json`**: outcome, termination reason, physical
  step count, policy decision count, MERGE commit step, final
  intervention rate.

## 6. Reading Success / Collision / Timeout episodes

Start with `outcome_index.csv` for the whole evaluated scope, then open
`selected_episodes.json` to see which maneuvers (up to 5 by default per
category, or every one with `--render-all`) were picked to represent
each category. From there, for each rendered maneuver:

- Open `rollout.gif` for a quick qualitative read (what did the ego do,
  did it merge cleanly, did an intervention fire).
- Open `trace.png` for the quantitative story (see Section 7).
- Open `rollout_4panel.png` for a compact 4-moment summary suitable for
  a slide or paper figure.

A `timeout` episode with `merge_commit_step: null` means the policy
never chose MERGE within the horizon (it kept choosing KEEP/FOLLOW/STOP)
-- check `trace.png`'s Action row and TTC/gap rows to see why.

## 7. Using trace.png for Reward tuning

`trace.png` stacks, over the same physical-step x-axis:

1. **Behavior Action** (KEEP/FOLLOW/MERGE/STOP over time; post-
   commitment auto-executed frames are shaded gray -- not a fresh
   decision).
2. **Ego speed**
3. **Remaining merge distance `d_m`**
4. **Target Front/Rear TTC and gap**
5. **Reward** (Reward V0 total, per step)
6. **Intervention** (0/1, whether `downstream_status != OK` that step)

A vertical red dotted line marks the MERGE commit step (if any). To
answer "why did the policy MERGE at this frame?", look at what
Front/Rear TTC and gap were doing just before that red line -- a
reward-shaping question about whether the policy is merging too early/
late relative to a genuinely safe gap is exactly what this plot is
for.

## 8. Comparing Reward V0 vs a future Reward V1

Run this pipeline once per checkpoint (one trained under V0, one under
a future V1 config) with the **same** `--scope explicit
--maneuver-ids ...` list, then compare `trace.png`/`rollout_4panel.png`
side by side for the same maneuver under each checkpoint. Because
`MergeEnvironment`, the 14D observation, and action semantics are
identical across both runs, any visible behavior difference is
attributable to the reward change (or PPO's response to it), not to a
confound in the environment.

This pipeline does **not** compute or claim any aggregate V0-vs-V1
comparison by itself -- it only lets you look at matched individual
episodes.

## 9. Deterministic vs stochastic policy mode

- **`deterministic`** (default): the policy always takes the argmax
  action (`PPOPolicy.act_deterministic`). Fully reproducible with no
  seed. This is what a deployed/evaluated policy would actually do.
- **`stochastic`**: samples from the policy's categorical distribution
  (`PPOPolicy.act`), seeded by `--policy-seed` for reproducibility.
  Useful for seeing the spread of behavior the policy could produce,
  but a single stochastic rollout is one sample, not the policy's full
  behavior distribution.

On any physical step **after** MERGE commitment, the policy is not
consulted for a decision at all (see `src/training/rollout.py`'s own
commitment contract, mirrored exactly here) -- `trace.csv`'s
`keep_prob`/`follow_prob`/`merge_prob`/`stop_prob` columns are `NaN`
on those frames specifically so they can never be misread as a policy
decision.

## 10. Limitations -- do not over-interpret

- **This is a post-training evaluation, not a training-time replay**
  (Section 3). It tells you what the *final* checkpoint does, not what
  it did *during* training.
- **A handful of rendered episodes are still a small sample, not the
  whole picture.** Picking "the first up-to-5 success/collision/
  timeout episodes in sorted order" (or the full set with
  `--render-all`) is a deterministic, reproducible choice -- it is not
  "the most typical" or "the most interesting" set of episodes, and it
  says nothing about the checkpoint's aggregate success/collision/
  timeout *rate*. Use `outcome_index.csv` (which always covers every
  evaluated episode, independent of the render policy) or the training
  run's own W&B `train/success_rate` etc. for aggregate numbers.
  - **This tooling is not evidence of generalization.** By default it
  evaluates the checkpoint's own TRAIN maneuver scope. Evaluating on
  `--scope split --split validation` still only tells you about that
  fixed VALIDATION set's behavior for one checkpoint -- it is not a
  substitute for a proper held-out generalization study, and per
  `docs/ppo/P6_EXPERIMENT_GUIDE.md` Rule 5, VALIDATION results must
  never be used to pick between reward/hyperparameter experiments.
